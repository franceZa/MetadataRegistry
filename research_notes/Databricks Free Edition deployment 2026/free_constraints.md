# Databricks Free Edition deployment constraints (as of 2026-09-26)

## Can a GitHub-built package be copied into Free Edition workspace files or Unity Catalog volumes?

### Takeaway
Official documentation supports both storage routes in a normal Databricks workspace, and a September 2026 tutorial explicitly confirms that Free Edition has Unity Catalog, a workspace catalog, and a usable default schema. The strongest documented route for a wheel is a managed UC volume; the CLI uses `dbfs:/Volumes/...` for upload and a serverless environment uses `/Volumes/...` to install it. The documentation does not explicitly promise that every CLI upload API is enabled in every Free Edition account.

### Cited Findings
- The Free Edition limitation page says one workspace and one metastore per account; it does not list workspace files or UC volumes among unsupported features. It says custom *workspace storage locations* are unsupported. [Databricks Free Edition limitations, last updated 2026-07-20](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations).
- A Databricks tutorial explicitly states Free Edition workspaces have Unity Catalog enabled by default, Free Edition users have privileges on the workspace catalog and `default` schema by default, and shows `CREATE VOLUME IF NOT EXISTS <catalog>.<schema>.my_volume`. It also tells Free Edition users to upload files from their local machine through the workspace UI because outbound internet is restricted. [Load and transform data using DataFrames, last updated 2026-09-11](https://docs.databricks.com/aws/en/getting-started/dataframes).
- Unity Catalog volumes can store library files, including Python wheels, exported from CI/CD pipelines. Managed volumes use UC-managed storage. Paths for consuming files are `/Volumes/<catalog>/<schema>/<volume>/<path>/<file>` (or `dbfs:/Volumes/...` where supported). [What are Unity Catalog volumes?, last updated 2026-09-11](https://docs.databricks.com/aws/en/volumes).
- The Databricks CLI `fs` commands explicitly require the `dbfs:/Volumes` prefix for volumes. `databricks fs cp SOURCE_PATH TARGET_PATH` copies local files into a volume; `--overwrite` is available. The same reference says to use `workspace` commands for `/Workspace` files. [CLI `fs` command group, last updated 2026-09-11](https://docs.databricks.com/aws/en/dev-tools/cli/reference/fs-commands).
- The CLI `workspace` command group supports `workspace import`, `import-dir`, and `mkdirs` for workspace files and folders. `workspace import` takes `--file`, `--format` and `--overwrite`; `import-dir` recursively imports a local directory and strips notebook extensions. [CLI `workspace` command group, last updated 2026-09-11](https://docs.databricks.com/aws/en/dev-tools/cli/reference/workspace-commands).
- Workspace files can include `.whl` libraries and have a 500 MB individual file limit. Workspace file permissions under `/Workspace` expire after 36 hours for interactive compute and 30 days for jobs; a continuously running job needs restart within 30 days to retain access. [What are workspace files?, last updated 2026-09-11](https://docs.databricks.com/aws/en/files/workspace).
- For serverless notebook or job dependencies, Databricks accepts Python wheels or Python project directories in workspace files (`/Workspace/...`) or volumes (`/Volumes/<catalog>/<schema>/<volume>/<path>.whl`). Python script and wheel tasks require an environment configuration. [Configure the serverless environment, last updated 2026-09-17](https://docs.databricks.com/aws/en/compute/serverless/dependencies).
- Serverless may use `aarch64` or `x86_64` across runs, so wheel dependencies must support both architectures; pure Python `py3-none-any` wheels avoid this issue. Databricks says changing a custom package implementation used in a serverless job requires bumping its version for the job to pick up the update. [Configure the serverless environment, last updated 2026-09-17](https://docs.databricks.com/aws/en/compute/serverless/dependencies).
- Serverless compute has limited DBFS access and recommends UC volumes or workspace files. [Serverless compute limitations, last updated 2026-09-11](https://docs.databricks.com/aws/en/compute/serverless/limitations).

### Inferences
- For a package built in GitHub Actions, upload the wheel artifact from the GitHub runner to a **managed** volume with CLI `fs cp`, or to a workspace folder with CLI `workspace import`; reference the corresponding `/Volumes/...` or `/Workspace/...` path in a serverless job environment. This is a synthesis of the CLI, Free Edition UC tutorial, and serverless dependency documentation above, not an explicit Free Edition CI/CD recipe.
- A managed volume fits Free Edition's default UC storage and avoids the unsupported custom workspace storage location. Whether Free Edition permits all managed-volume CLI APIs should be verified against the actual workspace.

### Gaps
- No 2026-03-26-or-later Databricks page found that specifically demonstrates CLI uploading a `.whl` to **Free Edition**; normal workspace commands plus Free Edition UC support are the evidence.
- Databricks does not publish a Free Edition-specific maximum wheel size, volume capacity, or workspace-file quota on the cited limitation page; the general workspace file limit is 500 MB per file.

## Which authentication methods can deploy from GitHub, and which are confirmed in Free Edition?

### Takeaway
The September 2026 CLI documentation supports interactive workspace-level OAuth U2M, legacy PATs, and service-principal OAuth M2M as general authentication methods. Free Edition-specific documentation confirms no account console or account-level APIs and limits interactive sign-in methods; it does **not** explicitly establish PAT, service-principal, or GitHub OIDC availability in Free Edition. Workspace-level U2M is the most defensible first path for local deployment, while unattended GitHub deployment needs account-level capability validation.

### Cited Findings
- Free Edition has no account console or account-level APIs, no SSO or SCIM, and interactive authentication is limited to email OTP, Sign in with Google, and Sign in with Microsoft. [Databricks Free Edition limitations, last updated 2026-07-20](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations).
- For workspace-level CLI commands, Databricks documents `databricks auth login --host <workspace-url>` as the browser-based OAuth U2M flow. It manages short-lived tokens, while `databricks auth login --host <account-console-url> --account-id ...` is for account-level commands. [Authentication for the Databricks CLI, last updated 2026-09-11](https://docs.databricks.com/aws/en/dev-tools/cli/authentication).
- The same CLI page documents PAT authentication as legacy and recommends OAuth where possible. It also documents OAuth M2M for unattended applications and services. [Authentication for the Databricks CLI, last updated 2026-09-11](https://docs.databricks.com/aws/en/dev-tools/cli/authentication).
- The general auth guide classifies U2M as attended, M2M service-principal authentication as unattended CI/CD, and OAuth token federation as the recommended approach when using identity-provider tokens. These statements are platform-wide, not Free Edition-specific. [Authorize access to Databricks resources, last updated 2026-09-11](https://docs.databricks.com/aws/en/dev-tools/auth/).
- GitHub OIDC-style workload identity federation needs a federation policy associated with a Databricks service principal; the documentation says account admins configure workload identity federation policies. [Configure a federation policy, last updated 2026-09-16](https://docs.databricks.com/aws/en/dev-tools/auth/oauth-federation-policy).
- Service-principal roles are account-level roles, according to the general Databricks access-control documentation. [Roles for managing service principals, last updated 2026-09-11](https://docs.databricks.com/aws/en/security/auth/access-control/service-principal-acl).
- PAT authentication is enabled by default for Databricks workspaces in the general admin documentation, but workspace-admin PAT management requires Premium or above; this page does not identify Free Edition as a supported plan. [Monitor and revoke personal access tokens, last updated 2026-09-11](https://docs.databricks.com/aws/en/admin/access-control/tokens).

### Inferences
- Workspace-level OAuth U2M is a reasonable authentication attempt for a Free Edition user's local CLI because it does not use the blocked account console. The Free Edition sign-in choices may be used within its browser flow, but the cited pages do not explicitly certify U2M for Free Edition.
- GitHub OIDC federation is not safe to assume for Free Edition: its normal configuration requires an account-level service principal policy, while Free Edition has no account console or account-level APIs. This is an architectural inference, not an explicit published prohibition on OIDC.
- PAT availability is likewise uncertain. General documentation saying PATs are enabled by default does not prove a Free Edition user can create one; no Free Edition-specific confirmation was found.

### Gaps
- No official 2026-03-26-or-later Databricks page found explicitly saying whether Free Edition allows creating PATs, service principals, OAuth client secrets, or workload identity federation policies.
- No official Free Edition-specific page found proving GitHub Actions OIDC to Free Edition works or fails. A real account test or Databricks support statement would be required before recommending unattended OIDC as a reliable route.

## Can Free Edition run and schedule serverless Jobs using the deployed wheel, and what limits matter?

### Takeaway
Yes for serverless Jobs in principle: the Free Edition limits explicitly allocate up to five concurrent job tasks per account, and the general current Jobs docs support Python wheel tasks and schedules on serverless. A Free Edition-specific schedule walkthrough or published schedule quota was not found, so schedule availability should be stated as an inference from supported Jobs rather than an independently confirmed Free Edition feature.

### Cited Findings
- Free Edition users have **only serverless compute**; custom compute configurations are unsupported. It permits at most **five concurrent job tasks per account**, limits notebook serverless size and usage, restricts outbound internet to trusted domains, and may shut down compute for the rest of the day or (extreme cases) month after quota is exceeded without deleting data or settings. [Databricks Free Edition limitations, last updated 2026-07-20](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations).
- The Free Edition versus trial comparison says Free Edition has one serverless workspace, no classic compute, limited compute size and usage, and daily usage limits. [Sign up for Databricks, last updated 2026-09-11](https://docs.databricks.com/aws/en/getting-started/free-trial-vs-free-edition).
- Serverless Jobs support notebook, Python script, dbt, Python wheel, and JAR task types. Jobs can be created/run with the Jobs API, Declarative Automation Bundles, or Python SDK. UC must be enabled, which the Free Edition tutorial confirms. [Run Lakeflow Jobs with serverless compute, last updated 2026-09-11](https://docs.databricks.com/aws/en/jobs/run-serverless-jobs); [DataFrame tutorial, last updated 2026-09-11](https://docs.databricks.com/aws/en/getting-started/dataframes).
- The general Jobs documentation lists serverless Jobs as supported and recommended for Python wheel tasks. [Configure compute for jobs, last updated 2026-09-15](https://docs.databricks.com/aws/en/jobs/compute).
- The general Jobs UI supports time-based schedule triggers and manual runs. By default one run of a given job can be active at a time; further runs may be skipped when job concurrency is exceeded. [Automate jobs with schedules and triggers, last updated 2026-09-11](https://docs.databricks.com/aws/en/jobs/triggers).
- The notebook UI can create a scheduled notebook job on serverless compute. [Run Lakeflow Jobs with serverless compute, last updated 2026-09-11](https://docs.databricks.com/aws/en/jobs/run-serverless-jobs); [Create and manage scheduled notebook jobs, last updated 2026-09-14](https://docs.databricks.com/aws/en/notebooks/schedule-notebook-jobs).
- Serverless Jobs' notebook tasks cannot use task libraries; use notebook-scoped or job-level environment dependencies. Serverless runs have a **seven-day maximum runtime**. Serverless doesn't support compute-scoped libraries, init scripts, or most Spark compute configuration. [Serverless compute limitations, last updated 2026-09-11](https://docs.databricks.com/aws/en/compute/serverless/limitations); [Configure the serverless environment, last updated 2026-09-17](https://docs.databricks.com/aws/en/compute/serverless/dependencies).
- A Python wheel task on serverless needs its environment/dependency configured, and the environment can reference a wheel in workspace files or a volume. [Configure the serverless environment, last updated 2026-09-17](https://docs.databricks.com/aws/en/compute/serverless/dependencies).

### Inferences
- A Free Edition user should be able to create and schedule a **serverless Python wheel Job** with a wheel stored in a workspace folder or UC managed volume, subject to quota and permissions. The Free Edition docs explicitly establish Jobs and serverless, while task type, dependency, and schedule support come from general Jobs docs.
- Treat the five-task cap as **concurrent tasks**, not five total saved jobs or five schedules. A narrow job concurrency setting and a daily quota shutdown can cause a scheduled run not to execute when expected.
- A GitHub-built wheel with dependencies requiring live internet downloads may fail under Free Edition outbound restrictions. Prepackaged/pure-Python dependencies or approved package repositories need account-specific validation.

### Gaps
- Databricks does not state a Free Edition-specific maximum number of saved Jobs, schedules, Jobs API calls, runs per day, or precise daily compute allowance in the cited Free Edition limits. Do not substitute general paid-account quotas or free-trial limits.
- No Free Edition-specific page explicitly confirms a scheduled Python wheel task. General serverless Jobs scheduling and Python wheel support strongly imply it, but an account test remains the decisive check.
