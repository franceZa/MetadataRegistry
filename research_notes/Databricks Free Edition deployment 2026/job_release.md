# Databricks Jobs and human-deployed config releases (as of 2026-09-26)

## Which Jobs task and compute should run a release in Free Edition?

### Takeaway
Use a saved Lakeflow Job on serverless compute. A Notebook, Python script, or Python wheel task can all run there; choose based on where the **execution code** lives. The repository's `build/<env>/release/` directory is a config package, not a wheel, and should be read as files from a Unity Catalog Volume.

### Cited Findings
- Databricks Free Edition provides serverless compute only, does not permit custom compute configurations, limits Jobs to five concurrent job tasks per account, and can suspend compute when fair-use quota is exceeded. Its Sep 25, 2026 limitations page also says Free Edition has no reliability guarantee, support, or SLA and is for non-commercial use. — [Databricks Free Edition limitations, updated Sep 25, 2026](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations)
- Serverless Jobs support Notebook, Python script, and Python wheel tasks; serverless Jobs require Unity Catalog and standard-access-compatible workloads. — [Run Lakeflow Jobs with serverless compute, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/run-serverless-jobs)
- A wheel task runs packaged Python code and needs the wheel's package name and declared entry point. For serverless, its dependency is configured under Environment and Libraries. — [Python wheel task, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/tasks/python-wheel)
- A Python script task runs a Python file. Workspace files are recommended for scripts; a script can also be stored in a Volume, with the DBFS/S3 source option. Serverless dependencies use Environment and Libraries. — [Python script task, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/tasks/python-script)
- A Notebook task points to a workspace notebook or remote Git source, takes key-value parameters accessible through `dbutils.widgets`, and on serverless can use the notebook Environment pane or `%pip` for libraries. — [Notebook task, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/tasks/notebook)
- Serverless task environments can install wheels from `/Volumes/<catalog>/<schema>/<volume>/<path>.whl`; Python script and wheel tasks require an environment. Serverless can run on either `aarch64` or `x86_64`, so pure-Python wheels are preferable when feasible; Databricks says to increment a custom package's version when its implementation changes so Jobs pick up the new code. — [Configure the serverless environment, updated Sep 17, 2026](https://docs.databricks.com/aws/en/compute/serverless/dependencies)
- Databricks explicitly shows a Python wheel dependency at `/Volumes/main/default/my-volume/my-wheel-0.1.0.whl` in a job bundle. — [Bundle library dependencies, updated Sep 11, 2026](https://docs.databricks.com/aws/en/dev-tools/bundles/library-dependencies)

### Inferences
- For this repository, use `build/<env>/release/` as the **data/config input** in a Volume. It contains resolved JSON and `manifest.json` according to `src/mdf/package.py`; `pyproject.toml` defines a separate installable Python project. Do not configure the config directory itself as a wheel dependency.
- Practical options: (1) a small stable workspace notebook reads `release_id` and the Volume's config files; (2) a workspace Python script does the same and reads CLI args; (3) a built wheel with a real declared entry point installs from an immutable Volume wheel path and reads `release_id`. The wheel option requires a separate wheel build and job environment configuration. A new wheel version requires changing the job's dependency path or a deployment mechanism; a new config release does not.
- For Free Edition, prefer a single task initially so the five-concurrent-task cap and quotas are easy to observe. Test the chosen task, package install, and Volume permissions in the actual Free Edition workspace before promising operational reliability.

### Gaps
- The general Databricks docs and Free Edition limitations page do not expressly guarantee that every task subtype, dependency source, or external package index is available in every Free Edition workspace. Feature rollout, quota, and outbound network constraints require an in-workspace smoke test.
- This research did not verify the repository has a runnable wheel entry point or an ingestion entry point. The current `mdf` CLI in `src/mdf/cli.py` exposes validation, compilation, packaging, verification, diff, and trace commands; deployment execution code is a separate design decision.

## How should `release_id` reach the task, and what is the exact trigger syntax?

### Takeaway
Define `release_id` as a job-level parameter, then trigger an existing saved Job with a per-run `job_parameters` override. Parameter delivery depends on task type: notebooks and wheel keyword arguments receive key-value pushdown, while Python scripts and wheel positional arguments need an explicit `{{job.parameters.release_id}}` reference in the task argument array.

### Cited Findings
- Job parameters are key-value pairs and may be overridden when starting a run. They automatically push down to tasks that take key-value parameters; job parameters take precedence over same-key task parameters. JSON-array tasks do not receive automatic pushdown and must reference `{{job.parameters.<name>}}`. — [Configure job parameters, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/job-parameters); [Configure task parameters, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/task-parameters)
- Databricks identifies Notebook and wheel-with-keyword-arguments as key-value tasks, and Python script and wheel-with-positional-arguments as JSON-array tasks. — [Configure task parameters, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/task-parameters)
- Notebook code retrieves a pushed parameter with `dbutils.widgets.get("release_id")`; script task parameters arrive as command-line arguments and can be parsed with `argparse`; the parameter-use page describes wheel keyword arguments. — [Access parameter values from a task, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/parameter-use)
- The current CLI syntax is `databricks jobs run-now JOB_ID [flags]`, with `--json` accepting inline JSON or `@path` to a JSON file, and optional `--idempotency-token` and `--no-wait`. The same CLI page says `jobs submit` makes an unsaved one-time run that is not shown as a saved job and lacks the same serverless failure optimization. — [Jobs CLI command group, updated Sep 11, 2026](https://docs.databricks.com/aws/en/dev-tools/cli/reference/jobs-commands)
- The Jobs API 2.2 `POST /api/2.2/jobs/run-now` request body has `job_id`, `job_parameters`, and an optional idempotency token (at most 64 characters); retrying with a given token launches exactly one run. — [Jobs API reference, viewed Sep 26, 2026](https://docs.databricks.com/api/jobs/v2/job)
- A human can use **Run now with different settings** to override the job's parameters in the UI. — [Trigger a single job run, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/run-now)
- Databricks documents `databricks bundle run --params message=HelloWorld hello_job` for a deployed bundle; this is distinct from `databricks jobs run-now`. — [Bundle CLI commands, viewed Sep 26, 2026](https://docs.databricks.com/aws/en/dev-tools/cli/bundle-commands)

### Inferences
- A Windows PowerShell workflow can write a JSON file containing `{"job_id":12345,"job_parameters":{"release_id":"<approved-id>"}}`, then run `databricks jobs run-now 12345 --json '@run-now.json' --no-wait`. `@run-now.json` is the CLI's file-reference syntax; single quotes keep PowerShell from interpreting the `@` argument. Replace the example Job ID and release ID. The CLI reference requires the positional Job ID even if the JSON body also includes `job_id`.
- Notebook path: set job parameter `release_id`, call `dbutils.widgets.get("release_id")` in the notebook, then validate and resolve it to a Volume directory. Python script path: set its argument array to `['--release-id', '{{job.parameters.release_id}}']` (JSON syntax with double quotes in actual job configuration), parse with `argparse`. Wheel keyword path: configure a keyword-argument-capable entry point and use the job parameter's automatic key-value pushdown; test exact entry-point behavior because Databricks' wheel tutorial also describes its UI arguments as command-line arguments.
- Give every release-trigger attempt a unique idempotency token derived from an operator request or deployment transaction, not just `release_id`: the same release can legitimately be retried after a failed run. Record returned `run_id`, selected `release_id`, and the final run state.

### Gaps
- The current CLI reference shows JSON-body syntax rather than a dedicated `--job-parameters` CLI flag; do not rely on an undocumented flag. `--json @file` should be checked against the installed CLI version with `databricks jobs run-now -h`.
- The Jobs API reference does not promise that passing `release_id` overrides the library wheel path or notebook/script source path. Those are job deployment settings, so use a stable runner or deliberately update the job when runner code changes.

## How should a human publish an immutable Volume release, secure it, and roll back?

### Takeaway
Use a unique, never-overwritten Volume directory per config release and let the job resolve only a validated `release_id` beneath a fixed Volume root. Verify the release package before upload and again in the job before consuming it; retain prior releases and roll back by triggering the saved Job with the prior ID.

### Cited Findings
- Databricks CLI `fs` commands require `dbfs:/Volumes/...` paths. `databricks fs cp SOURCE TARGET -r` recursively copies a local directory to a Volume directory; `--overwrite` overwrites existing files. `fs ls` and `fs cat` can inspect Volume contents. — [FS CLI command group, updated Sep 11, 2026](https://docs.databricks.com/aws/en/dev-tools/cli/reference/fs-commands)
- At runtime, Unity Catalog Volume files are addressed with `/Volumes/<catalog>/<schema>/<volume>/...`, including wheel dependency paths. — [Configure the serverless environment, updated Sep 17, 2026](https://docs.databricks.com/aws/en/compute/serverless/dependencies)
- Reading or listing Volume files requires `USE CATALOG`, `USE SCHEMA`, and `READ VOLUME`; creating, deleting, or updating files requires those plus `WRITE VOLUME`. — [Privileges for Unity Catalog volumes, updated Sep 11, 2026](https://docs.databricks.com/aws/en/volumes/privileges)
- Databricks says any user with `CAN MANAGE RUN` or higher on a job can override job parameters, so a default parameter value is not a security control. — [Parameterize jobs, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/parameters)
- A saved Job defaults to one concurrent run; queueing can hold runs when concurrency limits are reached (up to 48 hours), while a nonqueued run can be skipped. — [Configure and edit Lakeflow Jobs, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/configure-job)
- Serverless auto-optimization may retry failed tasks by default; it can be disabled for workloads that must execute at most once. — [Run Lakeflow Jobs with serverless compute, updated Sep 11, 2026](https://docs.databricks.com/aws/en/jobs/run-serverless-jobs)
- Free Edition has no account console or account-level APIs and does not provide enterprise security customization. — [Databricks Free Edition limitations, updated Sep 25, 2026](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations)

### Inferences
- Proposed layout: `/Volumes/<catalog>/<schema>/<volume>/config-releases/<env>/<release_id>/manifest.json` plus the resolved JSON files. Use an ASCII `release_id` such as a version plus full or abbreviated Git SHA; the exact format is a project convention. The runner should accept only a strict allowlisted ID pattern (for example `[A-Za-z0-9._-]+`), reject traversal, join it under a fixed root, and verify the resolved path remains there. Do not let a parameter supply arbitrary absolute paths.
- Human deployment sequence: (1) fetch the approved CI artifact at its exact commit or tag; (2) run the repository's `mdf verify-package` against the local `build/<env>/release/`; (3) choose a new `release_id` and confirm the target path is absent; (4) copy the directory with `databricks fs cp <local-release-dir> dbfs:/Volumes/<catalog>/<schema>/<volume>/config-releases/<env>/<release_id> -r` **without** `--overwrite`; (5) inspect/verify files in the Volume; (6) trigger the saved Job with that `release_id`; (7) review final run state and the run's recorded ID. Because directory copy is not documented here as atomic, only trigger after all files have been copied and verified. This is a derived procedure from the CLI and repository packaging behavior.
- Give the operator/upload identity Volume write access and the Job run identity only read access where possible. Restrict who can edit the Job and invoke it with arbitrary parameters. Preserve prior release directories; rollback is another run with a prior verified `release_id`. Rollback of configuration alone does not reverse prior writes to Delta tables or external systems; processing must be idempotent or have a separate data recovery plan.
- The repository's manifest hashes listed config files, but is itself unsigned. An attacker with permission to change both configs and manifest can replace both coherently. Treat its verifier as accidental/tamper detection within a trust boundary, and bind approval to an external trusted digest/commit or a signed artifact if adversarial tampering matters. Do not overwrite a published path. This follows from `src/mdf/package.py` and the documented Volume write privilege model.
- Prefer a saved Job with max concurrent runs 1 for initial rollout. Decide whether to enable queueing and whether serverless retries are acceptable for the actual ingestion semantics. A successful CLI trigger only confirms a run was requested; inspect the returned `run_id` and final state before calling deployment successful.

### Gaps
- Databricks' `fs cp` documentation does not guarantee an atomic directory publication or an immutable/WORM Volume directory. These properties need the project's no-overwrite procedure, permissions, and an in-job verification check.
- The source docs do not establish that Free Edition supports a service-principal-based run-as workflow for this account. Validate the available identity and privilege controls in the actual workspace; avoid basing the deployment on account-level APIs unavailable in Free Edition.
- No live Databricks workspace was connected for this research, so the exact user privileges, Volume name, job ID, CLI version, and Free Edition behavior remain untested.
